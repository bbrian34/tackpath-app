# TackPath API v1: known issues

These came out of the independent security review of draft PR #38. The high
and medium findings H1, H2, H3, M1, M3 and M5, and the low findings L1 and L7,
are fixed on `claude/api-v1`, each with a failing-first test in
`tests/api/hardening.test.mjs`. The items below are not fixed yet. Each says
what it is, why it was left for later, and what fixing it means.

## Open findings from the review

| Id | Severity | Issue | Where | Planned fix |
|---|---|---|---|---|
| M2 | Medium | **DNS rebinding.** A webhook host is resolved and checked against private and reserved ranges, then `fetch` resolves it again. A host that changes its DNS answer between the two could reach an internal address. The response body is never read or returned (blind), and only port 443 over HTTPS is allowed. | `supabase/functions/_shared/tp_api.js`, `runWebhooks` (check, then `deps.fetch`) | Send webhooks through an egress proxy that applies the same blocklist when it connects (for example Smokescreen), or connect to the checked IP directly with the host name as TLS server name. |
| M4 | Medium | **Overlapping worker runs, one slow customer delays the rest.** The worker sends up to 25 deliveries one after another with a 10 s timeout each (up to 250 s). The claim lock is 2 minutes and cron runs every minute, so a delivery still in flight can be claimed again (sent twice, one attempt used twice). A customer endpoint that always times out delays the other companies' deliveries in the same run. | `tp_api.js` `runWebhooks`; `69_public_api.sql` `tp_api.claim` (2-minute lock) | Send in parallel (`Promise.allSettled`) with a 5 s timeout, lock for 5 minutes, take at most a few deliveries per endpoint per run, and have `report` ignore a result whose attempt number does not match. |
| L2 | Low | **Two requests at once with the same Idempotency-Key.** The second gets a 500 (unique-index conflict) instead of the first answer. Nothing is created twice. | `69_public_api.sql` `tp_api.handle` (idempotency) | Take `pg_advisory_xact_lock` on (key id, idempotency key) before the lookup. |
| L3 | Low | A malformed percent sign in the URL path (for example `/orders/%E0`) is a 500 instead of a 404. | `tp_api.js` `matchRoute` (`decodeURIComponent`) | Catch the decoding error and answer 404. |
| L4 | Low | Without a Content-Length header the whole body is read before the 1 MB check. JSON nesting depth is not limited (very deep JSON ends in a 500 from the database). | `tp_api.js` `handleApi` | Read the body as a stream with a byte cap; refuse JSON nested deeper than 20 levels. |
| L5 | Low | One client key can use up the company's 10 webhook endpoints. One key can create about 60,000 live jobs an hour (120 batches of 500). | `69_public_api.sql` `run` (`webhooks.create`), `handle` (batch limit) | Limit endpoints per client label; add a daily order cap per company. |
| L6 | Low | `developers.html` allows inline scripts (`script-src 'unsafe-inline'`). Its company session is in `localStorage` under `tp_dispatch_org`, shared with the dispatcher page, so a script injection anywhere on tackpath.com could take it and create API keys. | `developers.html` line 9 and the session helper | Move the script to its own file, remove `'unsafe-inline'`, and keep the developer session separate from the dispatcher's. |

## Left open by the fixes themselves

- **Dispatch does not write `tp_order_id` yet.** After H1, an API order follows a route only when dispatch writes its TackPath order id (`ord_...`) on the route stop or package (`tp_order_id`). The dispatcher page and the manifest import do not do this today, because app pages were out of scope for this change. Until they do, API orders are tracked on their intake job (the pending job the API created). Tracking a routed API order needs a dispatcher change: when an API order's job is merged into a route, copy `tp_order_id` onto the stop.
- **The intake tracking-number check reads every route of the company.** It collects the package codes on all of the company's jobs once per request (one batch of up to 500 orders shares one pass). Measured on PostgreSQL 16: 108 ms for 1,500 routes of 20 stops (30,020 codes). It grows with the company's job history. Planned fix: keep the codes in a table maintained from the queue (the `stops` rows), so intake does one indexed lookup.
- **A 409 for a taken tracking number tells the caller the number exists in the company.** Intake refuses a tracking number that is already on any job of the company (H1). A client key can use this to learn whether a given tracking number is in the company's data, nothing more. It sees no route, stop, driver or proof of delivery. The answer is rate limited like every request.
- **A key prefix can be locked out for a minute.** After 10 failed attempts for one key prefix in a minute, more attempts with a wrong secret get 429. In the gateway, the right secret still works. In an edge instance, the right secret still works if the key worked there within the last 10 minutes; otherwise it gets 429 for up to a minute. Prefixes are only visible inside the key and on the company's developer page.
- **The caller's IP comes from proxy headers.** The edge function reads `cf-connecting-ip`, then `x-real-ip`, then the first `x-forwarded-for` entry. Whether Supabase's proxy lets a client set these headers has not been verified on the live platform. If a client can, the per-address limit can be dodged, but the per-key and per-prefix limits still apply. Check this during the pilot (DEPLOY.md, step 6).
- **Statement timeout.** `alter function public.tp_svc_api set statement_timeout = '5s'` was considered and not used. On PostgreSQL 16, a statement timeout set on a function does not cancel the statement that calls it (tested: a 2 s sleep ran 2,010 ms under a 500 ms function setting). Instead the work is bounded by design: lists read stored values; reads process at most 200 queued rows of the caller's company; processing stops after about 2 seconds; the triggers do one indexed read and at most one insert. A role-level timeout for the API (a dedicated database role for the edge functions) is the real backstop and needs an operator decision.
- **Webhook signing secrets are stored as plain text** in `tp_api.webhook_endpoints.secret`, in a schema no public role can read. The sender needs the raw value. Moving the secrets to Supabase Vault is a follow-up.
- **Order status lag.** Lists and webhooks see a change once it has been processed: within about a minute (the worker), or at once for the company's own reads. Webhooks report each status the order passed through, in order, from the recorded times.
- **The Deno wrappers have not run on Supabase.** `supabase/functions/api/index.ts` and `api-webhooks/index.ts` only wire secrets and clients around the tested shared code. They first run at the pilot.
